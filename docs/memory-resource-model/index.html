01总体结构：Agent、内存池与连接关系

Agent描述谁在执行，MemoryPool描述数据存放位置；连接与资源约束共同描述访问能力和性能。

蓝色为执行者，绿色为内存与放置，浅金色为通路、性能与执行。该图展示整体设计；Profile为可选方法模型，物理句柄由后端单独维护。

规划器处理的是带属性的资源图。访问连接关联Agent和MemoryPool；Method保存参考性能并包含候选Route；每条Route关联执行者、源池、目标池和资源用量，可选校准库补充Profile。同一对内存池可以有多种传输方法，多条Route可以共同消耗同一个Resource。ID对规划器是不透明标识，不通过名称推断物理位置。

非对称与不规则连接

源→目标和目标→源是两条有向Route。需要不同参考参数时，用端点条件区分的Method规则描述，或由条件Profile细化。多个连接可以引用相同的共享资源。

硬件结构由配置实例表达

System、Socket、Die、NUMA是CPU平台的组织信息。平台适配器把它们转换为Agent、Pool、连接与资源约束；规划器内部不需要这些类型。

核心边界

同一规划算法接收920f-lx、A800或H800的资源图。CPU模板可以用名为socket、die的分组表达重复和共享关系；这些只是模板中的标签，编译后只剩Agent、Pool和资源连接。

容量、服务能力和运行状态分开保存

MemoryPool保存可管理的总容量；运行时快照保存剩余容量、已预留量与预算。Resource保存服务上限；Profile保存特定方法在给定条件下能达到的速度。一块内存有多大，与某个执行者能多快访问它，是两项独立属性。

AllocationDomain将允许跨池回退的候选Pool组成集合；CapacityGroup识别同一物理容量的别名；MemoryArena管理真实backing及空闲缓存。它们均使用通用ID。多个逻辑池可以共享一个服务资源，例如DDR8–11；同一个池也可以同时受内存服务、跨socket互联和执行者发射能力限制。资源表示有效共享瓶颈，无须与物理控制器一一对应。

03数学描述：容量约束与服务约束

3.1 内存容量

∑jQjpj,k+Rk≤Ck
Qⱼ：本次新增分配大小；pⱼ,ₖ：实际落在池k的字节比例；Rₖ：未计入j的已有占用和预留；Cₖ：分配器可管理的容量预算。

容量约束全部使用整数bytes，覆盖所有同时存活的源、目标和临时数组。容量按实际映射页数计，包括尾页对齐；payload按请求字节计。分配完成后，以实际段映射替代理想比例。

3.2 基础性能与可选方法模型

T(Q) = Lstartup + Q / Breference
Q使用GiB，B使用GiB/s；T为秒，L = startup_us × 10⁻⁶。启动开销与内存访问延迟是不同参数。

基础模板保存参考带宽、共享服务能力，以及已知的访问延迟或传输启动开销。访问延迟用latency_ns，传输启动开销用startup_us；未测量时省略，表示未知。参考带宽取校准中的稳定大块测点；CPU参考访问速率采用已有最大核数测点，核数条件保留在校准文件中。

Tactivity = CostModel.estimate(target, Q, conditions) （可选）

只有需要更精确预测时才加载方法模型。target引用具体访问连接、搬运方法或计算方法；Profile保存供代价模型解释的参数，也可为Resource补充读写服务修正。大小曲线、CPU核数、并发流数、DMA在途深度分别命名，不共用含义模糊的parallelism。基础硬件加载与容量规划不依赖这些数据；小消息或少量执行核的耗时预测需要相应方法参数。

3.3 共享资源约束

∑i∈A(t)ar,ixi(t)≤Cr,xi≥0
A(t)：当前活动集合；xᵢ：payload GiB/s；aᵣ,ᵢ：每GiB payload消耗的资源工作量；Cᵣ：该资源每秒可服务的工作量。

一条P2P copy每传输1 GiB payload，通常需要源HBM读取1 GiB、目标HBM写入1 GiB，以及源TX/目标RX端口各1 GiB。对同池copy，读写工作量合计为2 GiB。资源只按实际关联关系收费。

读写共用服务能力时，可将资源容量归一化为1：读取成本为read_GiB/Bread，写入成本为η·write_GiB/Bwrite，二者服务需求相加。基础模型取η=1；可选校准可补充写服务放大系数，表达具体方法的有效写成本。

∑i(riBread+ηiwiBwrite)xi≤1
rᵢ、wᵢ是每GiB payload对应的读/写GiB数。read、write、copy、triad分别为(1,0)、(0,1)、(1,1)、(2,1)。

Resource.kind区分bandwidth与execution_slots。带宽资源沿用GiB/s；槽位资源用整数slots描述提交核、执行队列或在途请求上限，ResourceDemand.service=occupancy表示活动持续期间占用多少槽位。零payload的注册、同步与计算使用Activity.fixed_us；它们不能因为字节数为0而立即完成。

3.4 有限工作量与执行依赖

每个活动i有以GiB计的剩余payload工作量qᵢ，由Activity.payload_bytes / 2³⁰初始化；每次调用的固定流量另外计入对应资源需求。求解当前服务率后，推进到最近的完成事件；释放已完成活动占用的资源，激活依赖满足的后续活动，再求解。

Δt = mini∈A qi/xi，　qi ← qi − xiΔt

对带宽活动，默认服务分配可使用渐进填充的max-min共享；固定时间活动还要推进自己的计时器，槽位占用持续到相应阶段结束。提交、传输、轮询若先后发生，应拆成阶段，不能把它们的固定时间无条件取max。平台方法可增加串行队列、优先级或分组服务规则。算法操作稀疏约束矩阵和小型阶段DAG，无须逐周期模拟硬件。

同一框架中的两类限制

可选Profile限制“这个方法独自运行能有多快”；Resource限制“多个活动一起运行总共能占用多少服务”。两类限制共同进入求解，一条通路可以同时受多个资源约束。

04加权交织：连续地址，明确的物理放置

PlacementPlan描述虚拟地址区间到MemoryPool的映射。它既可表达多块HBM交织，也可表达HBM＋DDR混合。计划先用整数权重和条带描述，分配后物化为真实的页/段列表。

05传输方法、异步执行与共享带宽

5.1 CPU、SDMA、CUDA、MPI使用相同接口

传输请求描述源、目标、长度和依赖，Method描述可选搬运方法，后端执行能力检查、注册、提交与完成。CPU load/store可以作为计算活动的访存需求，copy/SDMA/CUDA/MPI则可以作为独立活动进入计划。

只有依赖边要求顺序。后端支持独立进展并有执行资源时，计算A可与传输重叠；计算B等待目标可见；缓冲区回收等待所有消费者和传输完成。

SDMA把数据搬运交给设备，提交与轮询仍消耗控制核；用execution_slots资源、阶段耗时和ProgressCapabilities共同表达控制成本。对重复执行，可复用映射和注册，分别计算首次准备与后续温态传输。

5.2 A800与H800为什么要采用不同的资源绑定

图中为GPU0相关实测值。A800的P2P与主机传输共享GPU PCIe端口；H800将NVLink peer端口与PCIe端口分开，最终仍共同消耗目标HBM服务。

A800数值演算

设两条流各搬运128 MiB，同时执行GPU1→GPU0 P2P与Host→GPU0 H2D。单独耗时约5.91 ms和5.35 ms；按共享GPU0 PCIe RX 23.38 GiB/s计算，合计256 MiB需要约10.69 ms。这个值是共享约束的模型演算，说明独立通路带宽不能相加。

5.3 集合通信保留算法级阶段

四rank ring allgather可以展开成“本地复制＋三轮邻居交换”。每轮使用源节点TX和目标节点RX资源；转发rank的串行调用还占用其进度核。知道算法时展开小型DAG；内部算法不可见时，也可以直接使用该集合通信的整体profile。一次预测选择一种计费粒度。

5.4 可执行命令、估价活动与进展能力

MemoryCommandPlan包含明确的source/target字节区间、opcode、Method、Route、queue和依赖。ByteRangeRef用kind区分slot与external，再给出计划符号、offset和size；它不直接引用导入对象ID。InvocationContext由InvocationStamp、事件端口和本次ExternalBinding表组成。copy具有等长操作数，并按解析后的物理区间判断重叠；普通copy不隐含memmove。queue由后端绑定执行者并验证权限，Route与实际页面来源匹配，交织区间按来源交集拆为合法命令。

CostPlan只用于estimate_schedule，不能提交执行。MemoryQueries.describe_operands把配方与显式外部端点表转换为OperandEnvironment；cost_plan从命令和这份环境生成访存与传输活动，不查隐式全局符号表。运行时用resolve_operands从实际MemoryBinding及本次导入对象得到同形的环境，validate_commands与submit使用相同范围解析规则。GraphExecutionPlan组合kernel调用与字节命令，kernel始终由上层图执行器执行。

7.1 从物理发现到进程可用视图

open_runtime(hardware, policy, calibration)加载可移植模板，由后端发现物理对象。current_scope()分别返回实际可执行Agent、可分配Pool、可访问Pool和执行槽位；view(scope)在后端权限内生成ResourceView。上层只使用该视图中的对象与连接。describe_bindings()可显示OS NUMA编号、CPU集合和设备标识用于诊断；规划器不解析这些标签。跨进程共享实体内存前，各参与者通过capacity_authority()核对同主机容量协调者的 opaque 身份；空值表示独立进程计账。这一身份属于现场映射与通信生命周期，不进入硬件模板和偏移量放置计划；通信模板单独记录已初始化Group的现场合同，恢复时核验。持久性能校准使用另一份稳定签名：保留CPU与固件、频率策略、按rank排列的CPU授权和线程数、资源图、生成切分的成员与顺序、以及实际二进制；排除boot ID与作业容量锁的inode。性能匹配只选择路由，不授予映射权限。

后端先求执行权限、内存权限、设备权限与应用选择的交集；容量协调器再扣除占用和已授予的配额。BudgetSnapshot.pools给出每个可分配分区的上界，groups按CapacityGroup去重，constraints表达跨多个分区共享的额度。规划器直接使用这组可行性约束，不按核数或rank数平均切分DDR容量。

例如同一DDR域四个分区分别可准入1、2、3、4 GiB，进程获准访问全部成员时可用上界是10 GiB；若只允许前两个则为3 GiB。若该进程另有6 GiB域额度，完整域视图也只能准入6 GiB。两个进程可同时查询到相近的系统剩余，但最终预留由共同协调器串行准入；查询值不能相加当作容量承诺。

“都由同一DDR控制器服务”只产生共享带宽约束，不自动把四个OS容量分区合成一块无限制本地内存；同域回退仍限于获准成员。多Pool上界也不能绕过共同cgroup或设备配额。导入远端共享页面只增加映射/引用，物理容量始终归其owner账本。accessible_pools与allocatable_pools分开：被排除的新分配目标仍可能允许导入已有共享页，因此保留其访问通路；它不重新进入本地分配域的回退成员。导入权限由共享句柄与后端访问授权检查。

7.2 LX2 DDR：容量分区、分配域与共享带宽

节点有16个DDR放置分区、4个Die级DDR控制器、16个独立HBM服务。DDR0–3、4–7、8–11、12–15各构成一个AllocationDomain。域允许分配器在成员间选择容量；四个成员引用同一个DDR Resource，用于累计读写服务需求。

[pools]
ddr = { per = "cpu", capacity = "discover", bind = "local-ddr", service = "ddr" }

[domains]
ddr_domain = { per = "die", members = "ddr" }

[resources]
ddr = { per = "die", read = 149.92, write = 141.37, sharing = "read_write" }

这些名称都是用户定义的标签。解析器只认识per、members等关系属性。DDR0–3是不同容量分区，容量可相加；若多个逻辑Pool实际指向同一物理容量，后端让它们引用同一个CapacityGroup，账本只计算一次。AllocationDomain决定候选范围，CapacityGroup决定容量去重，Resource决定带宽竞争。三者分别建模。

例如每个分区各剩2 GiB，DDR0优先的6 GiB请求可以依次从DDR0、DDR1、DDR2取得页面，并在后端支持时映射为连续虚拟地址。返回的AllocationInfo.segments记录实际放置。总读写仍共用149.92/141.37 GiB/s的服务约束；不能按使用了三个分区计算三倍带宽。若请求禁止回退或缺少合法连续映射能力，分配返回具体失败原因。

7.3 Eager：按块增长、缓存、延迟释放

MemoryPool是资源图中的可分配目标；MemoryArena是有状态的分配对象，可覆盖一个分配域中的多个Pool；也可直接传入单个Pool ID，形成单成员Arena，适用于A800/H800的单卡HBM等场景。Arena可以按页块使用buddy或分级空闲链表，向后端申请大块，再从块中满足请求。默认Arena由运行时配置按current_scope()创建，可通过arena_ids()/arena(id)取得；上层使用更窄视图时，通过create_arena(view, options)创建范围受限的Arena。请求先尝试preferred_pool；只有allow_domain_fallback为真，才尝试同域中获准的其他Pool。

页粒度空闲块→同域其他成员→预算允许则增长→记录实际页段
void eager_step(MemoryArena& arena, CompletionToken finished,
                const std::string& local_pool) {
    auto allocation = arena.allocate({
        .bytes = 20ULL << 20,
        .preferred_pool = local_pool,
        .allow_domain_fallback = true,
    }).value();
    void* pointer = allocation.data().value(); // always aligned to arena.page_bytes()
    const auto& actual = allocation.info().segments; // actual pools after fallback
    // Run tensor work using pointer; finished covers its last asynchronous use.
    (void)pointer;
    (void)actual;
    auto released = arena.release(std::move(allocation), finished);
    if (!released) throw std::runtime_error(released.error->message);
}

增长按grow_by_bytes批量获取backing；free先等待last_use以及该区间已登记的共享消费者全部退役，再进入缓存；导出映射仍保留时，只能按相容共享契约复用子区间。trim只归还无活动使用、无映射引用的空闲backing；retain_idle_bytes决定希望保留的空闲量。Allocation为move-only RAII句柄，record_use登记异步使用；析构把已登记但尚未完成的内存移入retired队列，不立即复用。调用者必须登记外部异步使用或先完成同步。

每次成功分配的指针均按池的有效页粒度Q对齐，收费长度为ceil(bytes/Q)×Q。池同时声明4 KiB与2 MiB映射页格式时Q为2 MiB，小页也按2 MiB块管理；这不表示小页已物理合并为大页。内核透明大页是实际物理合并，不增加池声明的映射粒度；仅声明4 KiB格式的池仍可按4 KiB规划偏移与尾部。AllocationInfo同时报告Q和实际物理页类别。小张量可由上层在同placement的页级allocation中显式子分配；另选基础页Arena也是一种策略。

页级分配与页内张量子分配

MemoryArena.allocate仍返回按page_bytes对齐的Allocation；池声明混合4 KiB/2 MiB映射页格式时，有效映射粒度Q取2 MiB；透明大页的实际大小另行报告。这约束底层allocation/backing，不要求每个张量单独分配一页。上层可在同placement的页级slot中按BufferBinding.view_offset_bytes和alignment子分配张量。backing获取/映射粒度、placement条带粒度、对象对齐、TensorView区间是四个不同属性；条带是Q的整数倍，对象对齐可以小于Q。

例如4096个同时存活的4 KiB缓冲区，按64 B对齐紧密打包，合计16 MiB，只需8个2 MiB页，而不是4096次独立页分配所需的8 GiB。收费按唯一backing计算。大页内部各对象不能独立重映射；只有要求独立重映射、独立placement或导出隔离的对象，才设置independent_mapping并取得独占、页对齐的区间。对共享页的迁移和回收，检查页内所有仍活跃对象及外部消费者。

7.4 资源配方：地址、backing与映射分阶段兑现

MemoryRecipe不包含张量或算子。AddressLayout给出每个region的长度、页粒度和slot整数offset；BackingRequest给出具体Pool、owner和物理字节数；PageMapping关联虚拟区间与backing区间。ResolvedPlacement保存有序页面来源，供上层离线打包。所有偏移和长度在计划中都是整数，未出现真实base地址。

prepare_addresses只预留地址并返回PreparedAddresses；reserve对当前预算准入；acquire_backing取得该owner负责的实际物理页；bind建立映射及访问权限，返回MemoryBinding。共享配方先agree_layout并exchange_backing，细节见11.13。各阶段可分别调用与缓存，地址准备不隐含物理分配。

// Stage 1: no physical allocation; slot() returns a reserved virtual address only.
std::shared_ptr<PreparedAddresses> prepare_memory(
    MemoryRuntime& runtime, const ResourceView& view, const MemoryRecipe& recipe) {
    return runtime.prepare_addresses(view, recipe.addresses).value();
}
// Stage 2: may run much later, using the same offline offsets and reserved VAs.
std::unique_ptr<MemoryBinding> activate_memory(
    MemoryRuntime& runtime, const ResourceView& view, const MemoryRecipe& recipe,
    std::shared_ptr<PreparedAddresses> addresses, MemoryArena& cache) {
    MemoryArena* caches[] = {&cache};
    auto budget = runtime.snapshot(view, caches);
    auto estimate = runtime.estimate(view, recipe, caches).value();
    if (!estimate.feasible) throw std::runtime_error("placement no longer fits");
    auto lease = runtime.reserve(view, recipe, budget.epoch, caches).value();
    auto backing = runtime.acquire_backing(view, recipe, *lease).value();
    return runtime.bind(view, recipe, std::move(addresses), std::move(backing)).value();
}
离线offset配方→预留VA→容量准入→获取backing→映射并授权

validate_recipe先检查所有引用和范围，再验证placement段按offset有序、非空、对齐、无重叠且完整覆盖slot，随后检查映射覆盖、Pool来源、共享权限和相容的重叠slot；它不证明张量生命周期。estimate给出按唯一backing计费的容量需求、可复用缓存与新增量；caches明确可参与的Arena。reserve检查传入的budget_epoch，将缓存和新增额度记入PlanLease；acquire_backing兑现额度，失败时释放本次新增资源和未兑现预留。

MemoryBinding保留地址、实际backing及布局代际，slot(id)仅在绑定有效时返回可用指针。record_use登记异步最后使用；unbind等待quiesce并保留VA。BackingSet可以继续保留，供同一图再次绑定或顺序图切换；物理页只在所有物理映射和所有者引用释放后归还。共享子区间的内容复用使用独立的退役协议，不要求每轮销毁整个backing映射。

7.5 统一句柄：指针、共享backing与重映射

AllocationInfo给出请求长度、实际映射长度、地址空间、页粒度、实际Pool段、backing mode、shareable/remappable和generation。data()只在当前进程具有合法映射时成功；远端内存不伪装成本地指针。GPU指针带有设备地址空间语义。

std::unique_ptr<MappedRange> alias_pages(
    MemoryRuntime& runtime, Allocation& allocation, VirtualReservation& target) {
    auto backing = allocation.export_backing().value(); // requires shareable_remappable backing
    const auto q = allocation.info().page_bytes;
    return runtime.map(target, std::move(backing), {
        .backing_offset_bytes = 0,
        .target_offset_bytes = 0,
        .size_bytes = q,
    }).value();
}

需要共享、页级重映射或多个虚拟地址别名的计划在分配前指定BackingMode::shareable_remappable。后端可用Linux的memfd/shm共享映射，或设备的虚拟内存接口实现；不支持时明确拒绝该请求。export_backing返回拥有生命周期的不透明对象，既可以查看后端导出句柄，也可交给map/rebind封装；上层不必自行管理裸文件描述符。

MappingCapabilities给出后端最大单块backing、VA region及映射长度；未知值为空。规划时超过限制，可合法分块则拆为多块，否则拒绝，不能等同于总剩余容量足够。map只能映射到本系统持有的VirtualReservation，源偏移、目标偏移和长度均按双方有效粒度对齐；partial_backing_map表示能否只映射根的一部分，multiple_mappings表示能否同时存在多个虚拟地址别名。能力查询接受BackingMode；支持多个映射的backing才可建立额外别名。rebind必须先通过quiesce取得覆盖受影响使用者的QuiescenceToken，在安全点更新映射、递增generation并失效旧地址相关注册。它映射同一批物理页，不改变NUMA放置；跨池迁移另建分配与传输计划。一次多区间更新需要独占安全点与失败回滚，不承诺硬件原子切换。

private_movable用于进程私有的单池缓冲区：整根匿名页在暂存地址与图预留地址之间移动，同一时刻只有一个有效映射。该映射内的普通Tensor子视图可共享所有者；跨进程导出、独立页重映射、交织页和多地址别名使用FD backing。匿名根在acquire时真实触碰全部页后才返回，移动不增加物理容量收费；内核可用时保留透明大页。该模式不继承到fork子进程，子进程需要新运行时和分配。

图编译器仅在未指定backing、无共享合同及独立页需求的单池slab上选择此模式，并查询后端能力；不支持时使用共享映射模式。显式指定的模式不被改写。每个可移动slab对应一个完整根，导出和交织的偏移布局保持通用规则。逻辑页粒度Q与实际透明大页大小分别报告。

匿名根的稳定收费标识与当前映射的字节标识分开：运行时和外部Tensor通过同一进程私有地址域描述重叠，避免把同一指针误判为两块独立内存。映射替换仅在安全点进行，普通失败返回前恢复旧映射；无法安全恢复时终止进程，不覆盖其他映射。Linux后端在成功移动后保留原地址占位，失败恢复使用不可覆盖已有映射的方式。

Allocation、SharedBacking及MappedRange共同维持引用；只有最后映射和异步使用结束，物理容量才可归还。PlanLease把已兑现额度交给BackingSet，销毁Lease只撤销未兑现部分。显式大页与普通页的物理语义见memfd_create；共享映射、页对齐和地址替换规则见mmap。

7.6 预算查询与预分配策略

预分配是应用策略，单独放在runtime-policy TOML中，也可通过ArenaOptions传入。硬件TOML保持机器资源描述。API显式选项优先于运行时配置，其次是默认值；环境变量只由前端转换成同一组选项。运行时先安装协调域的总上限，单个Arena的选项只能在该域剩余额度内细化，不能绕过总上限。

选项含义
hard_limit_bytes / hard_limit_fraction二选一，限制总backing占用。比例基于当前内存视图中可管理的唯一物理容量，计入别名去重和域配额。
preallocate_bytes / preallocate_fraction二选一，初始化先取得多少实际backing。比例基于已解析的hard limit；与运行中的增长上限分开。
allow_growth / grow_by是否允许按需增长及增长块大小；增长不能超过域和Arena的限额。
retain_idletrim希望保留的空闲缓存量，不影响仍活跃的分配。
page_size / backing固定分配与映射粒度，选择普通或共享可重映射backing；后端检查可实现性。

下载eager策略 · 下载预规划策略。domain_rule匹配AllocationDomain.rule，为视图中每个匹配域创建Arena；本例为LX2每个可见Die的DDR域。每个域的比例分母分别计算。多个rank共用域时，由协调运行时分配额度并共享容量账本，不能让每个rank各占80%。初始预分配完成后才返回初始化成功，并实际触页或调用设备分配接口核验放置；仅保留虚拟地址或ftruncate不算占有物理容量。它可减少运行中争抢，但普通可换出内存的预分配不等于系统级OOM保护。

快照同时报告活跃、空闲、已预留、延迟回收及系统可用量。系统可用量要扣除其他额度承诺，按cgroup、设备与页类别等限制取可准入量，不能把Arena自身缓存再次算作系统剩余。跨CapacityGroup汇总时，还要满足BudgetSnapshot.constraints中的共同额度，例如同一cgroup的总剩余额度；不能逐池重复使用这笔额度。

C = live + idle_available + idle_reserved + retired
headroom = max(0, H − C − unbacked_reserved)
available ≈ idle_available + min(headroom, system_available)

例如H=64 GiB，已持有C=24 GiB（活跃16＋空闲8），另有未兑现预留4 GiB，系统尚可准入60 GiB，则可提供约8＋min(36,60)=44 GiB。缓存中已预留的块仍包含在C中；未兑现预留只扣一次。该值是容量建议，不等于可立即满足的最大连续块；largest_cached_block_bytes、Pool放置限制和页类别仍需检查。外部进程可能改变系统剩余，最终以实际物化结果为准。

JAX也提供预分配比例及按需分配选项；具体增长行为取决于allocator模式。本接口明确区分初始占用和硬上限，避免把两者隐含合并。参见JAX GPU memory allocation。

统一账本与实际驻留是两组信息

模型arena、通信arena、权重副本及外部框架存储都登记到同一容量协调器。PhysicalAllocationRecord用后端核验的物理identity、owner和CapacityGroup记录已经占用的backing；import_memory可携带这份记录，导入别名只增加引用，不能重复扣容量。外部分配已计入系统占用时，登记只归属既有占用，不能再次从system_available扣同一笔，也不能靠重复登记制造可用额度。

observe返回MemoryObservation：唯一物理分配记录、逐分配的ResidencyObservation，以及可获得的未纳管占用。resident_bytes未知时为空，complete说明是否覆盖全部区间；驻留位置来自页面/设备后端观测，不由目标placement标签推断。驻留采样不隐式触页。预算预留、已持有backing、实际驻留分别展示；RSS或导入VA长度不能直接当作唯一HBM占用。AF3通信arena也进入同一账本，不能游离于模型HBM上限之外。

7.8 给定端点与模式，查询传输成本

MemoryCostModel同时提供传输与直接访存成本。candidates枚举公开Method/Route中的合法选择；estimate接收源/目标TransferEndpoint、payload、method、executor与前提状态。estimate_access接收Agent、读写方向和实际页面来源，评价零拷贝视图的消费成本；建映射本身只计准备开销，不能再额外计一遍不存在的payload复制。端点是按offset排序的Pool分段，可表达交织和远端拼接视图；不能把不同页面来源压成一个“HBM平均带宽”。CostContext给出实际执行槽位、当前活动、view_epoch及是否计入准备开销。

CostEstimate estimate_transfer(MemoryRuntime& runtime, const ResourceView& view,
                               const TransferQuery& query, const CostContext& context) {
    auto candidates = runtime.costs().candidates(view, query.source, query.target).value();
    if (candidates.empty()) throw std::runtime_error("no legal transfer method");
    // query.method/executor select a candidate. Endpoint page layout is explicit.
    return runtime.costs().estimate(view, query, context).value();
}
Submission copy_slice(MemoryRuntime& runtime, const ResourceView& view,
                      MemoryBinding& binding, const InvocationContext& invocation) {
    MemoryCommand command{};
    command.id = "copy-input";
    command.opcode = MemoryOpcode::copy;
    command.source = ByteRangeRef{MemoryRefKind::external, "input", 4096, 65536};
    command.target = ByteRangeRef{MemoryRefKind::slot, "staging", 0, 65536};
    command.method = "selected-copy-method";
    command.queue = "selected-copy-queue";
    command.wait_ports = {"input-ready"};

    auto valid = runtime.validate_commands(view, MemoryCommandPlan{{command}}, operands);
    if (!valid) throw std::runtime_error(valid.error->message);
    // submit re-resolves under retained leases; this query is not an execution permit.
    // The runtime resolves both operands, validates routes and retains their owners.
    return runtime.submit(view, MemoryCommandPlan{{command}}, binding, invocation).value();
}

7.9 公共事件与失败后的资源保留

CompletionToken带invocation和binding_generation。EventService负责导入外部CPU task、CUDA事件或MPI request，并提供query/wait/join/request_cancel/release。release释放调用者的句柄；运行时已登记的使用关系保留独立的事件引用，直到确认内存访问停止。ExternalEvent的句柄与owner仅存在于当前进程，不进入离线TOML。内存命令和kernel完成事件可以在同一执行DAG中衔接；错误传播与数据可见性由对应后端适配器落实。

Submission分别返回source_reusable、target_visible和finished。前者只允许重用该传输的源，不能越过其他读者；target_visible表示目标可消费；finished覆盖整个已接受命令集合。状态为pending/succeeded/failed/cancelled，并独立报告accesses_stopped。只有相关访问确实停止且全部消费者退役后才能复用物理区间；超时、取消请求或peer失效本身都不证明设备已停。

提交前全部失败返回Result错误；若部分命令已经接受，则返回Submission中的accepted_commands及submission_error，并持续持有相关allocation、映射和注册，直到其finished确认访问停止。不能以异常展开直接释放内存。每次replay使用参与者范围内唯一的新invocation；同一ID不得用于不同绑定。旧事件不得作为新一轮写入或退役的完成证明。持久只读state的初始化事件可作为显式输入依赖复用，导入与join时用当前InvocationContext建立可追踪的桥接。默认实例不可重入，并发执行需要独立实例或显式证明可共享的资源与状态。映射/权限更新失败时的恢复仍由部署策略决定，不假装成原子事务。

09硬件模板与可选校准库

一份简短TOML描述硬件资源，另一份可选TOML描述具体方法的执行性能。同构机器共用模板，物理编号和可用容量由后端发现。

基础模板独立展开成通用资源图；校准库作为独立输入补充性能模型。两台同构机器的物理编号可以不同。

configs/*.toml · 必需

对象原型、重复关系、连接、参考带宽、共享资源和必要能力要求。带宽统一为GiB/s。没有profiles、size、operation或核数采样表。

calibration/*.toml · 可选

大小曲线、cpu_cores、方法读写成本等校准结果。通过access:规则名、transfer:规则名、resource:资源名关联基础配置。

9.1 固定的是语法，名称由配置定义

固定语法配置自行命名的部分解析规则
groups / agents / pools / resourcesuma、cowos_superdie、compute、memory、infinity_fabric等名称是ID，不是硬件类型；对象名支持字母或下划线开头，后续可用数字和连字符。
count / perper引用的原型名称按引用依赖排序展开，声明顺序无关；groups可以省略，也可存在多个独立根。
same(x) / different(x)x可以是任何已定义的分组或对象原型比较两个端点所属的x实例，不识别Socket、Die、NUMA层级。
local / same_pool / any端点选择器，如compute[0]local要求池位于Agent实例之下；同层兄弟对象用same(共同分组)。[i]按各最外层分组内的原型展开顺序选择；没有分组时使用全局序号。
per / service / use任意共享资源名称per定义归属；service引用内存服务；use可引用source、target或executor的资源。
between / within / edges任意端点原型与作用域名称显式有向edges可描述非对称拓扑；省略edges时展开有向全连接，带宽可以共用标量或逐边列出。
bind / require后端角色名、硬件事实键和值bind是不透明发现契约；require只比较后端返回的同名事实，不内置CPU/GPU型号分支。

die_link与infinity_fabric对解析器完全等价。重命名时同步更新引用即可；通用编译器不会把某个名称解释为固定层次或某种总线。groups、agents、pools的原型名在三者之间唯一；resources有独立命名空间。

校准条件也在编译阶段消除层级关系

calibration/0.4中的样本可写source、target、executor、method等模板选择条件，例如hbm:same(die)&!local。通用模板编译器使用同一份临时实例关系解析这些条件，输出CalibrationCase(method、route、executor、profile、sample)。公开PerformanceDatabase只保留具体ID匹配和数值维度；成本插件不解析ID路径，也不保存另一份Socket/Die知识。声明顺序和任意对象重命名后，解析出的测点选择必须等价。运行时节点数也必须同时用于硬件与校准展开。校准先对完整逻辑拓扑编译，再按ResourceView过滤可选执行者与通路；权限裁剪不重新编号。

9.2 完整硬件模板与校准文件

基础模板：920f为57行、A800为40行、H800为42行。H800的一条different(gpu)规则仍展开56条有向P2P连接，端口共享关系由资源引用保留。

9.3 用通用流量需求替代操作枚举

传输默认消耗源读一次、目标写一次；可用traffic = { read = 2, write = 1 }描述其他流量比例。规划器不需要认识triad名称。执行方法的实际流量放大、核数和scratch等细节由可选模型补充；GPU读取kernel也属于方法校准。

模板中的参考带宽与共享Resource容量分开：前者限制单条连接，后者限制同时使用该资源的活动总量。校准模型再补充特定方法在给定大小或执行资源下的限制。LX2的SDMA3同HBM测点为22.86 GiB/s，跨die为28.94 GiB/s；前者不再充当所有路径的共享引擎上限。两者保留为通路样本；共享引擎约束待并发证据辨识后再加入，不能用孤立路径吞吐代替公共容量。

9.5 解析与规划边界

  1. 后端发现硬件，用require核对事实，并给出运行时重复数量。
  2. 通用编译器按per依赖展开对象，解析where、共享服务和有向路径。
  3. 把分组关系、校准条件及选择表达式转成明确的对象ID、Method.routes、CalibrationCase和资源引用；规划器不解析层级名称。
  4. 后端提供物理绑定和可管理容量；按需加载独立校准库，再进行分配与传输规划。

生产通用模板展开器为HardwareTemplate；硬件TOML保留资源与参考参数，独立校准由Calibration解析。设计期Python参考解析器已退出生产工具链。新增uma、cowos_superdie或infinity_fabric无需修改解析器；若引入新的分配/传输机制，则由对应后端实现bind角色。

9.6 与现有系统的对应关系

Realm用Processor–Memory和Memory–Memory affinity表达带宽与延迟；hwloc提供按initiator区分的读写带宽和延迟。基础资源层采用这类简洁表达。

StarPU将总线校准与任务性能模型分开；NCCL在调优层按算法、协议和消息大小估计耗时。可选方法层采用这种分离方式；共享资源约束参考SimGrid的服务率约束模型。

11上层：资源感知图编译器

张量放置、通信改写、alias选择和地址复用属于资源基础设施的上层。生产路径先由GraphCapture.prepare_torch完成图改写，再由Python GraphMemoryCompiler把最终缓冲区需求编译为MemoryRecipe；通信候选由独立CommunicationCompiler生成。

本节用C++形式表达概念协议，便于核对基础设施边界；这些声明不代表已提供同名C++图编译器。生产规划器复用Python图表示和算子信息，通过绑定调用C++资源查询与执行接口。

生产字节接口以Model.h为准，GraphPlanning.h仅描述上层概念职责。纯compile/compile_model通过MemoryQueries查询资源；prepare_model是需要MemoryRuntime的准备入口，只预留VA并取得pending容量lease，物理backing由PreparedProgram.materialize获取。前者不包含张量、算子或张量生命周期分析；图编译部分只通过公开资源视图、预算、放置解析、成本与映射接口使用前者。两层不读取对方的空闲链表、OS NUMA编号或内部拓扑分组。

浅金色为通用资源接口与后端。具体放置、通信分解、调度和alias决策都在上层；硬件后端不接收神经网络算子。

多进程联合准入时，已成功的进程保留容量预留，失败的进程根据剩余容量重新规划，避免所有进程反复争抢同一块优先内存。进入集体资源补齐回调前，全体撤销图容量预留并同步，保留偏移计划和虚拟地址；仅在通信资源增长时整体重编。任一进程出现不可恢复错误时，各进程关闭本地计划并归还预留。

较大的冷编译期间，系统空闲内存可能下降。若最终估算报告容量组的实际可用量低于规划采样，规划器可在下一次尝试中留出等于已观测下降量的余量。只有账本、epoch及独立Pool限额未变，且Pool可用量没有被额外截断时才学习；新预留或限额变化会清除余量，空闲缓存仍可复用。一次实际物理短缺也会学习同账本两次采样间其他未截断容量组已观测到的下降，每组取历史最大值，不跨组套用，也不累加采样。紧凑布局重试在退出优先布局的异常处理后开始，先释放失败布局的元数据。这是本次准备内的放置策略，既不修改公开预算，也不替代运行时准入；准备结束后即清除。

ModelExecutor、ModelExecutionInstance、LayoutProvider、DistributedLayoutLinker与ReuseProof在下文只作为设计概念；C++图示例不构成已安装SDK的调用示例。当前用法见Python指南。

11.1 图中只有两类存储，能力用属性表达

BufferRequirement按external / internal分类。external表示生命周期跨越本次图调用的边界，不等于必须由调用者管理。输入、显式传入的输出，以及权重、模型buffer和跨调用cache都属于external。internal包含中间张量、kernel workspace与通信staging；它们使用同一套容量、放置和复用规则。

边界类别属性与约束典型处理
external · 输入/输出所有者、读写权限、是否允许重定向/捐赠、调用后是否保留输出改写成destination参数。借用输入默认保留原值；输出地址由调用约定决定。
external · stateruntime_owned或borrowed、可变性、内容version、跨调用有效期只读权重可在prepare阶段复制到HBM，重绑定内部使用者；可变state要定义写回与版本失效。
internal大小、对齐、消费者、允许的Pool、生产/使用/退役依赖临时张量、workspace、通信缓冲区一起参与物理峰值与地址复用。

TensorView描述shape、stride、dtype和存储偏移；存储身份由BufferRequirement.id表达。多个view共用一个storage时只计一份物理容量，生命周期取所有别名使用者的并集。返回值若无法绑定到显式输出，或某个cache会逃逸，就必须提升到external，不能以internal提前回收。workspace只是来源标签，不能因此形成独立、无法共享容量的内存组。

ExternalContract.initial_location记录编译时已知的源端点，ready_port提供输入就绪依赖，用于权重迁移与保护性copy估价；未知位置保留为空并报告缺失信息，不能假设已在目标HBM。外部指针通过import_memory登记地址空间、字节区间、owner生命周期与已知Pool。它不把普通Torch存储自动变成可重映射backing，也不重复申请其已有容量。无法导出或不满足映射粒度时，使用显式复制；由资源提供者解析或拒绝未知放置，图编译器不自行猜测。

11.2 从算子获取的契约

KernelVariant提供消费者Agent、内部缓冲区需求、资源用量、计算成本及经过审核的AliasRule。operand_layouts引用有版本的LayoutDescriptor，由LayoutProvider查询真实storage_bytes、对齐、padding初始化和辅助缓冲区；blocked、packed、量化及后端不透明布局不压成普通shape/stride。布局转换由provider返回OperatorContract，workspace、复制与成本一同入图。同一算子的不同算法可能需要不同workspace，规划器应比较“kernel耗时＋workspace放置＋传输”，不能先固定workspace容量再选择算法。按worker/并行lane复制的临时空间应展开为实际实例，计入同时活跃峰值。

BufferUse记录数据读写区间和Activity；metadata_only不延长数据生命周期。Kernel契约还必须表达原地读写顺序、允许的布局、输入输出重叠条件，以及异步最后使用事件。未知或有外部副作用的算子形成opaque边界。循环、条件分支和动态形状通过图签名与guard限定；无法界定的内部大小使用保守上界或运行时子计划。

11.3 规划流水线与迭代关系

  1. 规范化：外部输出改为destination，合并storage/view身份，提取state版本、控制依赖、异步完成与kernel候选。
  2. 资源查询：取得每个执行者的ResourceView和协调预算。生成本地、远端、交织、迁移及常驻副本等少量放置候选。
  3. 通信分解：根据数据piece与接收者生成直接、共享、分层转发、分块流水等候选，加入所需staging及注册/完成/退役事件。
  4. 联合选择：用代价模型评价计算、传输、准备和并发竞争，选择kernel、placement、通信方案及合法alias，并改写执行图。
  5. 重新分析：插入copy、pack、gather、scatter或wait后，重新计算所有内部缓冲区的生命周期、页舍入和峰值；容量不满足时回退候选。
  6. 离线布局：在相同placement约束下复用地址区间，生成整数offset、BackingRequest和PageMapping。检查语义复用证明与实际映射相容性。
  7. 准备与激活：先预留地址、绑定可执行代码的地址参数；执行前再准入、获取物理backing、映射并初始化常驻数据。

图改写会影响临时内存和并发，放置又会影响通信方案，因此不是一次线性贪心即可保证最好。首版可用有界候选搜索和局部迭代；优化目标是最终执行图的耗时与容量可行性，而不是单独最小化跨域字节或内存峰值。

11.4 自动生成分层通信，不写Socket/Die特判

上层可以在原生算子编译完成后、生产图绑定前查询已发现的借用式消费请求，得到不含地址的算子标识、整数特化参数和输入/输出几何。已知消费算子可用独立合成数据校准候选路由；工作区仍由同一MemoryRuntime计费，各rank的偏移量配方随测量保存。配置的策略保持优先，最终输出Pool与算子二进制须精确匹配。已知通信组在正常准备阶段建立，推理时复用；校准与组创建计入准备时间，不算模型预热。

CommunicationRequest提供操作语义、带version和区间的DataPiece、接收者及消费方式。归约必须附ReductionContract，明确运算、类型、元素数、结合/交换性质与数值顺序；fp32的数学可结合性不等于允许浮点重排。缺少这些语义不能自动选择局部归约或改变rank次序。上层从公开Route的共享Resource引用和访问代价形成候选分组/有向切分：共享同一瓶颈的端点作为一个候选域，再比较域间入口、副本与分发。无需识别某条资源是否叫die_link、infinity_fabric或RoCE。

分组只是搜索候选，可以重叠、非对称或不构成树。编译器递归组合“发送一次＋域内共享/分发”等通用规则，并限制候选数量；每个候选都展开为完整传输DAG。后端负责提供合法的点对点、映射、注册和同步原语，CommunicationSynthesizer决定如何组合它们。

11.7 地址准备、物理分配与映射彻底分开

CompiledMemoryProgram与PreparedAddresses可长期缓存。BackingSet是实际物理容量的所有者，MemoryBinding表示当前哪些地址已经可访问。

struct PreparedProgram {
    CompiledMemoryProgram program;
    std::shared_ptr<memory::PreparedAddresses> addresses;
};
PreparedProgram prepare_graph(
    const GraphMemoryCompiler& compiler, const CommunicationSynthesizer& communication,
    const ExecutionGraph& graph, memory::MemoryRuntime& runtime,
    const memory::ResourceView& view) {
    auto snapshot = runtime.snapshot(view);
    auto program = compiler.compile(graph, view, snapshot, runtime, communication).value();
    auto addresses = runtime.prepare_addresses(view, program.memory.addresses).value();
    // Bind executable argument addresses/guards now; do not read unmapped storage.
    return {std::move(program), std::move(addresses)};
}
struct PreparedModel {
    ModelMemoryProgram program;
    std::shared_ptr<memory::PreparedAddresses> addresses;
};
PreparedModel prepare_model(
    const GraphMemoryCompiler& compiler, const CommunicationSynthesizer& communication,
    const ModelExecutionPlan& model, memory::MemoryRuntime& runtime,
    const memory::ResourceView& view) {
    auto snapshot = runtime.snapshot(view);
    SearchBudget search{32, 1000000, FallbackPolicy::reject};
    auto program = compiler.compile_model(model, view, snapshot, runtime,
                                           communication, search).value();
    // Evoformer/diffusion/confidence AND native workspace share one physical plan.
    // ProgramCall bindings link subgraph external buffers to model storage identities.
    auto addresses = runtime.prepare_addresses(view, program.memory.addresses).value();
    return {std::move(program), std::move(addresses)};
}
std::shared_ptr<ModelExecutionInstance> activate_model(
    const ModelExecutor& executor, const PreparedModel& prepared,
    const InvocationInputs& inputs, memory::MemoryRuntime& runtime,
    const memory::ResourceView& view) {
    // Guard actual inputs and state, admit capacity, acquire/map physical backing.
    return executor.activate(prepared.program, inputs, runtime, view,
                             prepared.addresses).value();
}
memory::CompletionToken run_model(
    ModelExecutionInstance& instance, const InvocationInputs& actual_inputs,
    const std::string& invocation_id, std::span<const memory::EventBinding> ready) {
    // actual_inputs contains imported storage handles AND actual view/layout metadata.
    memory::InvocationStamp stamp{invocation_id, instance.binding_generation()};
    return instance.run(actual_inputs, stamp, ready).value();
}

prepare_graph生成MemoryRecipe并预留VA，到这里没有申请图所需物理backing。slot()返回保留地址的数值，供代码准备和指针guard绑定；映射前不能读取数据或运行会访问该地址的kernel。普通操作系统可能为VMA等元数据使用少量内存，这与申请张量物理页分开计量。

激活时重新查询预算，reserve取得额度，再acquire_backing获取物理页，bind建立映射和访问权限。初始化图负责权重复制、布局转换及必要的state重定向；这些工作可在prepare/activate边界执行一次，而不是每次推理重复。反向解绑保留VA，等最后消费者退役、解除地址相关注册后再释放或转借backing。

独立的BackingSet允许图A与图B保留各自VA，在顺序执行时切换物理资源。若两图页面兼容，可以复用同一批物理backing；若HBM与DDR placement不同，则按新配方重新获取/映射，不能只改一个标签。正在被借用的输出、模型state、尚未完成的网络请求都会阻止回收。需要并发运行的图必须获得独立或明确共享的额度。

地址稳定也不意味着GPU graph、SDMA/RDMA注册和后端执行器必然允许重新映射；mapping_capabilities与注册代际共同决定是否需要重注册或重新准备。bind应完成该后端要求的访问授权；若不支持任意backing偏移，则把backing降为可独立映射的块，或拒绝该配方。切换耗时应包括unmap/map、页表更新、注册和必要的数据迁移。

不同时持有A/B全部backing可以降低物理峰值，但切换失败时A的映射可能已移除；需要可恢复性时保留旧backing至B激活成功，或采用双份预算。它是部署策略的选择，不把多地址映射更新包装成原子事务。

11.8 常驻state与缓存一致性

只读权重从DDR转至HBM时，保留源storage身份、内容version、目标副本及prepare完成事件，图参数表重定向到该副本。原权重修改、模型重载或新版本传入后，副本失效。可变buffer与KV/cache要指定唯一权威位置、更新顺序和调用结束是否写回；不能把它们当只读权重缓存。

持久化缓存保存无指针CompiledMemoryProgram、kernel/shape/control-flow签名、逻辑资源签名与外部state版本。进程重启后重新绑定资源和VA。每次激活检查容量epoch及权限；仅带宽校准变化可触发重新评分，拓扑/映射粒度变化则重新验证布局。旧raw指针不能写入跨进程计划。

11.11 整模时序：子图external不等于全程常驻

ModelExecutionPlan连接多个ExecutionGraph及图外原生调用。ProgramCall记录调用DAG、准确的repeat_count、retained_storage与CallBinding；CallBinding把子图局部buffer关联到模型级storage及区间。对子图是external的数据，在整个模型中仍可为internal；只有跨整模边界的数据才进入模型external集合。每个调用/迭代的局部事件与临时对象具有独立身份，不能因kernel或shape相同而合并生命周期。

AF3可表达为prologue → Evoformer steady/recycle → diffusion steps/samples → confidence。首版重复执行使用准确的正整数repeat_count、顺序执行和固定绑定：它表示重复同一操作，不自动把输出反馈到下一次输入；retained_storage只表达有效期。需要ping-pong、前次输出到后次输入或并发sample时，展开为明确的ProgramCall及CallBinding依赖。动态次数先在前端求出准确值并纳入模型签名/guard；0次调用从计划中省略，不把容量上界当作执行次数。图外原生算子的workspace与图内张量、pack和通信staging统一分析。

11.12 激活检查、保守路径与实现规模

ActivationContract给出ShapeBound、control_guards、state版本、donation授权、reentrant及fallback。InvocationInputs.buffers按模型storage符号传入本次ImportedMemory，arguments按模型ABI参数名传入ActualArgument：实际TensorView（dtype、shape、strides、storage和offset）与可选的实际LayoutDescriptor。普通strided输入逐项核对预期几何与存储界限；不透明布局经有版本的LayoutProvider核对provider、opaque_key、padding、实际存储大小、对齐及辅助缓冲区。元数据来自框架适配器或C++调用者声明，不能从裸字节内容推断dtype。

概念协议中的ModelExecutor.activate与ModelExecutionInstance.run表达激活、逐次参数校验和代际保护职责；生产中由框架适配器与PreparedProgram配合C++运行时承担，不提供这两个C++类。执行器从inputs.buffers构造一次InvocationContext.external，避免上层参数表与底层绑定表各自指向不同对象。shape、控制guard、端点、布局、state版本或donation不匹配时，按策略拒绝、重编译或使用容量已经重新验证的保守子计划。未知副作用算子保持opaque边界。

概念协议的SearchBudget用于表达候选数量与规划时间限制；它不是当前Python接口的参数。先构造显式Pool放置、copy、串行通信和保守复用的可行基线，再比较交织、迁移、共享与分层候选；达到预算时返回已经验证的基线，或按on_exhaustion明确失败。CostQuality缺少关键参数时不假设重叠或收益。容量、权限、语义和生命周期证明独立于性能估价，估价偏差不能授权非法复用。

物理图由MemoryRuntime只读提供；ResourceView.graph为可按Scope/epoch缓存的权限投影。Route可按需生成/缓存；历史参考展开器单节点LX2展开5120条Route；生产以HardwareTemplate与ResourceModel的实际输出为准。配方验证按映射区间与契约事件扫描：每个slot先与唯一映射表核对，再只比较活跃placement/共享契约的种类与计数，不逐对比较同址slot。64、128、4096个同址slot分别处理128、256、8192个端点事件，配对比较均为0；总体还包含排序的O(N log N)及输入区间处理成本。64 GiB/4 KiB配方也不展开为逐页字典。

11.13 跨进程零拷贝：共享契约也是复用条件

物理placement与共享契约分别表达。同样位于本地HBM的两段内存，一段可能纯本地使用，另一段已导出给其他进程；远端HBM也可以作为本进程VA中的一段。它们都可以参与复用，但不能只凭“都在HBM”或本地最后一次使用就判断安全。

BackingRequest指定唯一owner、Pool、大小与export_to集合。owner在该Pool取得可重映射的共享backing，其他进程可以整段导入、映射，也可以仅把其中选定页区间拼入自己的连续VA。整段导入是物理访问能力，不等于整段都在当前通信中活跃；SharingContract与SharedRange进一步规定哪些子区间在某个data_epoch由谁生产、谁消费、何时可以复用。

范围物理计费与映射复用条件
纯本地slotowner本地backing；没有远端使用契约本地全部使用退役，placement及映射约束相容
导出的本地slot物理页仍属于owner的Pool；多个导出映射不重复计费本地生产者和所有远端消费者的lease均退役，才能进入下一data_epoch
导入的远端slot本进程只保留映射与引用；物理容量记在owner，不记到本地HBM不能擅自free远端页；由约定的owner/协议分配下一次使用，本地VA复用也要检查全局约束
多来源拼接slot一个连续VA按多个PageMapping指向不同owner/backing/offset逐页检查物理来源、相位、权限、共享契约和相关参与者的退役条件

相同共享契约下，映射可以长期保留，按begin → producer ready → publish/acquire → readers finish → retire循环复用同一子区间；不必每轮unmap/map。映射引用固定的是backing的物理生命周期，消费者lease固定的是本轮子区间的内容生命周期。后端按backing与物理offset区间追踪lease；同一批页经多个VA或多个共享契约出现时，复用检查取所有重叠区间的活跃消费者并集，不能按每个VA独立判定。前者仍存在时，后者可以结束并允许下一轮使用。

从纯本地用途变成共享用途、或在两种共享协议间切换，也允许复用：先证明旧契约下所有参与者已退役，发布新的layout_generation或经过共同确认的契约切换，必要时撤销旧权限/注册，再启用新用途。若有仍可执行的旧kernel或未退役的远端读者，就不能复用。需要隔离时必须实际撤销旧映射或权限；不能只更新本地元数据。

两进程all-to-all的页拼接示例

取Q=2 MiB。rank0在HBM24取得4 MiB共享arena A，rank1在HBM25取得4 MiB共享arena B；每个arena按目标rank排列两个2 MiB块。消费者要求按源rank排列，则每个进程准备4 MiB连续recv VA：

接收者与VA offset物理来源来源区间
rank0 / recv + 0owner0 / arena A / HBM24offset 0，length 2 MiB
rank0 / recv + 2 MiBowner1 / arena B / HBM25offset 0，length 2 MiB
rank1 / recv + 0owner0 / arena A / HBM24offset 2 MiB，length 2 MiB
rank1 / recv + 2 MiBowner1 / arena B / HBM25offset 2 MiB，length 2 MiB

唯一物理backing合计8 MiB，每个owner收费4 MiB；两个recv映射不再额外收费8 MiB。每个recv的placement是有序的多来源页面序列；其数据来自邻近HBM的load/store，仍消耗对应访存与互联资源。零payload复制不等于零访存成本。消费者若要求可修改的私有副本，需显式物化，不能把只读共享视图当作私有输出。

所有规划结果都用offset，可打印、可交换

AddressLayout、BackingRequest、PageMapping、SharedRange及DistributedLayout全程不保存raw pointer、文件描述符或设备句柄。虚拟位置用participant / region / offset / length，物理来源用owner / backing / offset / length，并带Pool、权限和代际。下载可直接打印的offset审计示例。recipe_to_toml/layout_to_toml提供可交换表示，解析后先做结构与范围校验；一致性摘要基于规范化字段，不能直接对原始TOML文本求hash来判断语义相同。prepare_addresses以后才产生运行时base表；最终指针只是本进程base与offset的绑定结果，不回写离线计划。

审计输出按participant、region、virtual_offset排序，逐行列出owner、backing、backing_offset、Pool、权限、sharing_contract、layout_generation与data_epoch，并分别汇总VA长度和唯一物理backing。所有字节位置是整数，展示时可格式化为KiB/MiB/GiB。这份计划可直接交给另一个进程校验和绑定。

跨进程一致性：链接offset，再交换句柄

  1. 局部规划与全局链接：DistributedLayoutLinker收集各参与者的无指针布局，将导出区间、导入引用和复用约束链接为同一份DistributedLayout。共享子区间的owner/backing/offset由这份布局确定，不能让各rank按自己的空闲链表顺序各自猜offset。
  2. 规范化并确认：对成员、owner、尺寸、Q、页来源、权限、共享协议和generation排序编码，比较摘要。相同符号ID必须具有相同含义，且所有引用均在范围内。agree_layout成功后才形成LayoutAgreement；不要求各rank的真实VA相等。摘要相同证明布局一致；DataPiece对应关系及通信结果语义仍由上层编译器验证。
  3. 获取并交换：各owner只为自己负责的BackingRequest预留额度并acquire_backing。exchange_backing把导出句柄与已确认的backing ID、owner、大小和generation关联，导入方再次核对，不能用“相同Pool名”替代同一物理backing身份。
  4. 映射与发布：bind按每个参与者自己的base表建立页映射与访问权限，保留agreement和backing引用；所有需要的映射就绪后，进入约定的publish/acquire协议。
  5. 复用与故障：retire_shared的完成表示契约要求的所有参与者已退役，才允许下一data_epoch。超时或peer失败使该共享组失效；不能把没有收到的退役确认当作已完成。
std::unique_ptr<MemoryBinding> activate_shared_memory(
    MemoryRuntime& runtime, const ResourceView& view, const MemoryRecipe& local,
    const DistributedLayout& manifest, std::shared_ptr<PreparedAddresses> addresses) {
    auto agreement = runtime.agree_layout(manifest).value(); // digest, offsets, owners
    auto budget = runtime.snapshot(view);
    auto lease = runtime.reserve(view, local, budget.epoch).value();
    auto owned = runtime.acquire_backing(view, local, *lease).value(); // local owner only
    auto accessible = runtime.exchange_backing(*agreement, std::move(owned)).value();
    return runtime.bind(view, local, std::move(addresses), std::move(accessible),
                        agreement.get()).value(); // retains agreed generation
}

layout_generation描述映射/契约版本，data_epoch描述同一映射的第几次内容使用。稳定offset与共享句柄不保证数据可见性；发布/获取的内存顺序、完成事件与退役协议仍由后端落实。这与当前ExchangeBuffer的begin/publish/retire设计一致，可在稳定映射上保持低开销。
