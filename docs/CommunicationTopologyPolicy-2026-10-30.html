逐层共享/复制、分布式落点与带宽模型

推荐方案：任意深度的拓扑包含树；树之外有明确共享范围的容量资源；每个层级独立选择共享、复制与消费布局；跨层传输按chunk分配目的落点和发起lane。首版用资源总容量＋可选独占路径带宽，不要求用户填写完整并发曲线。

主设计文档定义通信语义、Torch兼容、graph依赖和生命周期。本补充细化策略搜索与配置，不修改实现，也没有新增性能实验。

1. 每个层级的选择可组合，副本落点是独立维度

“die间传一份，再die内传播”至少拆成四个维度：在哪些域生成额外副本、每份副本的物理片段放在哪些target、由哪个计算域执行push/pull、后继直接读/复制/pack。不要用一个hierarchical开关把它们绑死。

组合跨die行为目的die内部行为
全局源端共享不预复制；消费者实际读时穿过跨die路径。读源端片段，或直接生成自有packed结果。
die复制＋NUMA共享每片数据在每个目的die只建立一份副本。该die的NUMA共享这份分布式副本；没有完整本地副本的消费者仍付die内远端访问。
die复制＋NUMA复制同上。再为每个消费NUMA建立本地副本，后续本地读。
每NUMA直接复制各NUMA直接从源die得到自己的副本，跨die可能重复传相同片段。无需中继；适合作为简单基线，也可能因并发性或小消息更快。
分层复制＋直接消费布局按域建立适量副本。从分片直接生成本地packed/转置结果，不建立完整普通布局副本。

“某层共享”只是没有在该层边界预复制，不意味着没有跨边界流量。下层若决定本地物化而直接读取远端源，真实DAG可能退化为重复跨die复制，必须按实际数据流计费。某些片段也可保留源位置、另一些复制；小规模首版先限制到每个消息bucket一致的策略，避免搜索爆炸。

将来跨socket同理：socket间共享，或每socket一份；在socket内部又可每die一份或共享；再在die内部选择NUMA副本。共享策略要求地址能力、只读/写权限和lease合法；任意组合不是跳过这些条件。

2. 不先聚集：每个source/chunk可直接写目的die的不同位置

目的die的“一份完整副本”是逻辑概念，可以由分布在四个HBM target上的片段组成。比如A0/A1/A2/A3分别把源片段写到B0/B1/B2/B3；各进程映射这些片段形成逻辑完整视图。不需要A端先聚合，也不需要B端单leader接收全部数据。

等量输入、等能力target时，一一对应是简单候选；不存在必须匹配相同NUMA序号的硬件语义。数据量不等、部分NUMA无rank或容量不足时，按chunk拆开并轮转/加权分配；push执行器靠近source，pull执行器靠近destination，两者单独选。

放置目标应平衡的是归一化的关键资源负载，而不仅是入口字节：

对每个候选落点j，估计新增：
  写入/入口时间、后续读取/出口时间、域内转发时间、执行lane占用、容量。
目标：尽量降低各资源上的 Σ需求 / 有效容量 的最大值，
      并满足消费者关键路径与slot生命周期约束。

同构情况下通常接近平均分片；异构情况下按有效容量和消费权重加权。
“流量平均”也应限定同一时间窗口，不能只比较整轮累计字节。

die复制＋NUMA共享时，每块会被多个NUMA读，落点要同时计一次写入和多次远端服务；die复制＋NUMA复制时，还要计后续fan-out。均匀放置减少单HBM服务热点，但不能消除共享跨die cut的总容量限制。所有page位置在prepare完成；不在replay中轮换物理页，只轮转预建slot或执行顺序。

为控制实现复杂度，首版可用容量受限的加权轮转/贪心落点：每加一个chunk，选使最大归一化负载增加最小的target；随后做少量交换改进。2–8个target无需通用最优多商品流求解器。对4+2等不对称组同样适用；证据不足时保留flat计划。

3. 支持任意深度包含树，但不把每层都当成必经中继

推荐软件内部支持通用Domain树，kind只是标签。典型为host→socket→die→NUMA；也可省略die，或增加cluster、cache group、device partition。未来host上层可以有network locality group。任意深度的树和递归遍历成本很低，不需要先写死两层再迁移。

树回答“属于谁”，不完整回答“流量经过哪里”。新增显式Link/Fabric和容量资源作为补充：树可以生成默认候选路径，已知ring/mesh、直连、NIC亲和和共享cut用覆盖规则表达。hwloc也把距离/带宽矩阵作为层次结构之外的信息。

内存挂在拥有/服务它的domain：DDR pool可挂die，HBM target挂NUMA。实际OS暴露的多个DDR NUMA节点仍各自保留target身份，pool把它们共同关联到一个controller资源；不能因为挂在die就合并掉OS页放置和容量，也不能为每个别名重复生成一份带宽。

同样，“同socket不同die”的路径消耗die链路；“跨socket”的路径消耗inter-socket资源，但不应因树的祖先关系自动再扣一次不存在的die-link。路径包含哪些资源由拓扑路由规则决定，不能简单把所有祖先的带宽取min。

4. min带宽是有用的起点，但必须补上三项信息

对独占的一条长流，若源、目标、路径资源独立且每字节各消耗一次，吞吐上界可以用min(源可用速率、目标可用速率、路径容量)。用户提出的DDR A→DDR B正属于这个简化模型的候选。但这通常是上界，不能直接作为实测吞吐。

缺失信息为什么需要最小补充
资源共享范围四条流穿过同一128 GB/s cut，不能每条都分128；NUMA间150究竟是每对还是所有pair共享会改变结论。每个容量资源有唯一ID，路径引用它。aggregate只建一个；per_pair显式展开，必须有证据。
读/写字节计费与方向同一DDR控制器内copy，搬运M通常至少读M＋写M；两个独立controller则各服务M。push/pull的发起带宽也不同。资源声明计费口径；路径声明需求系数和方向。必要时加入独占路径实测上限。
发起并行度和消息粒度1核吃不满450 GB/s；小块、strided、短段与长流差别大，启动与尾部不能忽略。可选solo profile按操作、worker数、大小/布局bucket定义，不强迫手写整条曲线。
资源r的容量 Cr，流f速率 xf，需求系数 arf：
    Σf arf * xf ≤ Cr
流的独占执行上限：
    xf ≤ Bsolo(f, workers, size, layout)

固定一阶段工作量Df时，资源服务时间下界：
    max_r [ Σf arf * Df / Cr ]
再结合启动、阶段依赖、计算干扰和尾部估计关键路径。
这不是精确仿真；先用于排除明显拥塞的候选，再用实测校验相近方案。

例如copy在同一controller内读写M，若配置的是该controller读写合计C，需求为2M；不能再按M/C预测。跨两个独立controller，分别计读M、写M，互联再按其口径计M。写分配、RFO、cache复用可能改变物理流量，因此粗略系数只是模型；不能把应用copy读写总GB/s直接当链路payload GB/s。

die内DDR→某HBM还可能受die内fabric、发起端带宽、读写混合特性限制，因此不总是min(DDR,HBM)。DDR→DDR也必须计两端可用能力。若两个方向共享容量，显式配置sum约束；若独立，配置两个有向资源。未知时不能默认独立；保守模型必须标注假设，且不能把未知带宽写成0或无限。

5. 带宽数值分三层，不要求首版拟合完整曲线

层内容建议
基础配置，必需拓扑、共享范围、每个瓶颈资源的有效总容量、计费口径；容量可未知。先用少量可解释的固定值。优先使用可复现实测，规格值标记nominal，仅供粗排。
路径校准，可选但重要特定read/write/push/pull的独占吞吐、worker饱和点、启动延迟、真实stride/message bucket。自动读取校准profile；未提供时保守估计或禁用收益不明确的自动优化。
争用校准，后续可选共享资源在不同并发数/混合方向的聚合吞吐、上下界和误差。仅对关键路径补测，如1/2/4路；不做全机器全组合拟合。

“独占流量＋满载流量”两个数字比一个数字好，但必须定义满载场景：几条流、每条多少worker、是否双向、内存类型/页大小、消息大小，以及结果是每流还是聚合。两点不自动确定中间曲线；不要无依据线性插值。

最小实用模型是共享资源总容量＋每流独占路径上限。若观测聚合吞吐随并发显著变化，再添加按并发bucket的aggregate上限；那是对原资源约束的细化，不是额外再扣一次同样开销。

设计应保留来源、条件和不确定度，但不要求用户手填所有字段。平台拓扑配置与机器校准profile分开：前者稳定易读，后者由benchmark生成并按allowed CPU、频率策略、页模式和机器标识匹配。x86改频等变化应使相应执行/路径校准失效，不能继续用旧solo数值判定收益。

为了保持简单，可提供平台preset或重复条目的模板展开；内部schema保持规范化ID和显式资源引用。不要求配置文件把运行时rank拓扑写死，rank placement由实际启动绑定得到。没有die层的平台可省略该层，针对kind=die的prefer规则无匹配则跳过。

7. 策略搜索保持有界，目标是端到端关键路径

  1. 由合法能力和输出契约过滤候选：能共享映射不等于允许暴露borrowed输出。
  2. 按实际消费者分组，枚举少量复制层级：原始共享、每socket/每die/每NUMA副本，以及相邻两级组合；只生成有需求的副本。
  3. 对每个策略选择分布式落点；同构输入先试对应映射、轮转、加权chunk分片，避免集中单leader。
  4. 选择push/pull、参与lane和chunk大小；按资源总负载与消费者成本估计makespan，保留少数候选。
  5. 对差距明显且证据覆盖的候选自动启用；接近或参数未知则prepare期小范围A/B或保持基线。各rank共同commit同一计划。

性能证明是条件性的：可证明同一数据跨昂贵cut的逻辑重复量下降；不能证明更高的域内流量、更多副本、producer写出变慢和consumer远端读取一定能被抵消。优化目标计入通信后的使用，而不是只让collective计时变短。

强制策略应独立覆盖层级复制、落点、方向和lane，不用一个mode编码所有组合。prefer失败给解释并fallback；require在prepare报错；资源容量、别名、lease及计数一致性约束不可被强制开关绕过。

8. 首版复杂度边界与验证

值得首版就做的：任意深度树、内存pool/controller分离、显式共享资源、每层复制选择、分片落点、简单resource-load模型、explain输出。这些会决定API和正确归因，后补代价大。

可以后做的：完整mesh路由、每种混合负载的性能曲线、精确cache/coherence仿真、全局最优流量求解。首版用离线校准表和少量候选A/B即可，未知能力与容量保留unknown，避免虚假的精确数字。

验证应分别覆盖2socket/单socket、无die层、3+1/4+2rank、大小不均片段、HBM不足、单direction/双direction竞争。测每target物理驻留、写入/服务字节、实际lane占用和端到端耗时；共享路径的流量会出现在消费者阶段，不能只数通信memcpy。每条资源和计量基准在explain中可追溯，防止同一controller算四遍或同一有效吞吐既当路径耗时又重复扣资源。

依据：内存性能报告、通信归因报告；拓扑参考hwloc distances/memory attributes；页策略参考Linux NUMA memory policy。
